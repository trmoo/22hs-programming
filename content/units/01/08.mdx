## 생각 열기 — 코드는 있는데 실행이 안 된다

친구가 만든 Python 프로그램을 파일로 받았다. 열어 보니 코드가 제대로 들어 있다. 그런데 더블클릭해도 아무 일이 없다. 친구는 "내 컴퓨터에서는 잘 되는데"라고 한다.

<InfoBox variant="think" label="함께 생각해 보기">
코드가 같은데 왜 한쪽에서만 실행되는가? 프로그램을 실행하려면 **코드 말고 무엇이 더 있어야** 하는지 2차시의 내용을 떠올려 보자. 그리고 이 문제가 여러 사람이 함께 만들 때 어떤 일을 일으킬지 생각해 보자.
</InfoBox>

## 개발에 필요한 도구들

프로그램을 만들려면 도구가 여럿 필요하다. 각자 하는 일이 다르다.

생각 열기의 문제는 여기서 답이 나온다. 친구의 컴퓨터에는 **Python 인터프리터가 설치돼 있었고** 내 컴퓨터에는 없었다. 코드는 번역기가 있어야 실행된다.

</InfoBox>

## 디버거 — 실행을 멈춰 놓고 안을 들여다본다

<Term ko="디버거" en="debugger" desc="프로그램 실행을 원하는 지점에서 멈추고 변수 값과 실행 순서를 확인하는 도구" />는 논리 오류를 찾는 도구다. 5차시에서 논리 오류가 가장 찾기 어렵다고 했다. 프로그램이 멈추지도, 오류 메시지를 내지도 않고 그냥 답이 틀리기 때문이다. 디버거는 그 틀린 답이 만들어지는 과정을 보여 준다.

- **중단점** — 여기서 멈추라고 표시해 둔 줄이다. 실행이 그 줄에 닿으면 멈춘다.
- **한 단계 실행** — 멈춘 곳에서 한 줄씩 실행한다. 어느 줄에서 값이 틀어지는지 짚을 수 있다.
- **변수 값 보기** — 멈춘 순간의 모든 변수 값을 표로 보여 준다.

디버거가 없어도 `print` 를 끼워 넣어 값을 확인할 수 있다. 실제로 그 방법도 널리 쓰인다. 다만 확인하고 나면 끼워 넣은 출력문을 **반드시 지워야** 한다. 남겨 두면 쓰는 사람에게 알 수 없는 값이 보인다.

## 첫 프로그램으로 환경을 확인한다

환경이 제대로 준비됐는지 확인하는 방법은 짧은 프로그램을 하나 돌려 보는 것이다. 확인할 것은 두 가지다. **실행이 되는가**, 그리고 **한글이 깨지지 않는가.**

<CodeSample lang="python" caption="환경 확인용 프로그램" expect={"환경 확인 — 한글이 제대로 보이면 성공\n2 + 3 = 5\n"}>
{`print("환경 확인 — 한글이 제대로 보이면 성공")
print("2 + 3 =", 2 + 3)`}
</CodeSample>

<CodeSample lang="c" caption="환경 확인용 프로그램" expect={"환경 확인 — 한글이 제대로 보이면 성공\n2 + 3 = 5\n"}>
{`#include <stdio.h>

int main(void)
{
    printf("환경 확인 — 한글이 제대로 보이면 성공\\n");
    printf("2 + 3 = %d\\n", 2 + 3);
    return 0;
}`}
</CodeSample>

한글이 `?????` 나 알 수 없는 기호로 나온다면 코드가 잘못된 것이 아니다. **글자를 저장하고 표시하는 방식이 어긋난 것**이다. 이때는 파일을 UTF-8로 저장했는지, 명령 창의 글자 설정이 UTF-8인지 확인한다.

입력을 받는 프로그램도 확인해 두면 좋다. 아래는 이름을 받아 인사하는 프로그램이며, 입력으로 `정보` 를 주었을 때의 결과다.

<CodeSample lang="python" caption="입력이 되는지 확인하기" stdin={"정보\n"} expect={"이름을 입력하세요: 반갑다, 정보\n"}>
{`name = input("이름을 입력하세요: ")
print("반갑다,", name)`}
</CodeSample>

안내 문구와 결과가 한 줄에 붙어 나온다. `input` 이 보여 주는 안내 문구 뒤에 줄바꿈이 없기 때문이다. 문법은 2단원에서 다룬다.

<CodeTask lang="python" title="환경 확인 프로그램을 직접 쳐 보기" expect={"환경 확인 — 한글이 제대로 보이면 성공\n2 + 3 = 5\n"} hint="print 는 괄호 안의 내용을 화면에 내보낸다. 문자열은 따옴표로 감싸고, 숫자 계산은 따옴표 밖에 둔다. 두 번째 줄처럼 쉼표로 나누면 사이에 공백 하나가 들어간다.">

위의 환경 확인용 Python 코드를 **아래 칸에 직접 입력해** 두 줄이 그대로 나오는지 확인해 보자. 다 적었으면 준비된 개발 환경으로 옮겨 실행한다.

</CodeTask>

<InfoBox variant="tip" label="왜 붙여넣기를 막아 두었나">
코드를 복사해 붙이면 결과는 같지만 **괄호·따옴표·쉼표를 어디에 두는지가 손에 남지 않는다.** 처음 배우는 동안 자주 나는 오류가 대부분 이 부호에서 생긴다. 직접 쳐 보면서 한 번 틀려 보는 편이 빠르다. 위 칸은 붙여넣기를 막아 두었다.
</InfoBox>

## '내 컴퓨터에서는 되는데' — 환경을 맞추는 일

같은 코드가 컴퓨터마다 다르게 동작하는 원인은 대체로 셋이다.

1. **번역기가 없거나 판이 다르다.** Python이 설치돼 있지 않거나, 판이 달라 새 문법을 알아듣지 못한다.
2. **라이브러리가 없다.** 코드가 불러 쓰는 라이브러리가 이쪽에만 깔려 있다.
3. **글자 설정이 다르다.** 한글이 깨지거나 파일을 못 읽는다.

혼자 만들 때는 자기 컴퓨터만 맞으면 된다. 그런데 **여럿이 나눠 만들면 이 문제가 곧바로 걸림돌이 된다.** 나는 되는데 짝은 안 되고, 합쳐 놓으면 아무도 실행하지 못하는 일이 생긴다.

<InfoBox variant="info" label="공동 개발 환경이 필요한 첫 번째 이유">
그래서 함께 개발할 때는 **모두가 같은 환경을 쓰도록 맞추는 일**부터 한다. 같은 판의 번역기를 쓰기로 정하고, 필요한 라이브러리 목록을 적어 함께 두고, 글자는 UTF-8로 통일한다. 웹 기반 실행 환경이 수업에서 쓸모 있는 까닭도 여기 있다 — **주소만 같으면 환경이 같다.** 다음 차시에서 환경을 맞춘 뒤에 코드를 어떻게 나누고 합치는지 다룬다.
</InfoBox>

## 활동

<Activity kind="실습" title="두 환경에서 같은 코드를 실행해 비교하기" time={20}>

**1단계 — 웹 기반 환경에서 실행한다.**

위의 환경 확인용 Python 코드를 이 페이지의 실행 단추로 돌린다. 결과와 걸린 느낌을 적는다.

**2단계 — 설치형 환경에서 실행한다.**

같은 코드를 전산실에 준비된 개발 환경에 붙여 넣어 실행한다. C 코드는 컴파일 명령과 실행 명령을 각각 확인한다.

**3단계 — 표로 비교한다.**

| 실행 단추를 누른 횟수 | | |
| 컴퓨터의 파일을 읽을 수 있는가 | | |
| 인터넷을 끊으면 되는가 | | |

**4단계 — 일부러 어긋나게 해 본다.**

코드에서 따옴표 하나를 지우고 두 환경에서 각각 실행한다. **오류 메시지가 어떻게 다르게 보이는지** 적는다. 어느 쪽이 잘못된 줄을 더 빨리 알려 주는가.

**5단계 — 정리한다.**

"우리 반 수업에서는 어느 환경을 주로 쓰는 것이 좋은가"를 한 문장으로 적고 근거를 두 가지 든다. 4단계에서 지운 따옴표는 되돌려 놓는다.

</Activity>

## 더 알아보기

<MoreBox tag="심화" title="'디버그'라는 말의 유래">
프로그램의 잘못을 벌레(bug)라 부르고 그것을 잡는 일을 디버그(debug)라 한다. 1947년, 초기 컴퓨터 하버드 마크 Ⅱ가 오작동했을 때 기계 안에서 나방이 발견되었고, 작업 기록에 그 나방을 붙이고 "버그를 발견한 첫 사례"라고 적어 두었다는 기록이 남아 있다. 2차시에 나온 그레이스 호퍼가 이 일화를 널리 알렸다. 다만 bug 라는 말은 그 전부터 기계 고장을 뜻하는 말로 쓰이고 있었다.
</MoreBox>

<MoreBox tag="실무" title="필요한 것 목록을 파일로 남긴다">
프로그램이 쓰는 라이브러리 목록을 **파일 하나에 적어 코드와 함께 두는** 방법이 널리 쓰인다. 그 파일이 있으면 새 컴퓨터에서 명령 한 줄로 필요한 것이 전부 설치된다. "무엇을 깔아야 하는지"를 말로 전하지 않아도 되는 것이다. 사람마다 다른 것을 깔아 생기는 문제를 없애는 가장 간단한 방법이며, 다음 차시의 공동 개발과 곧바로 이어진다.
</MoreBox>

<MoreBox tag="심화" title="편집기와 통합 개발 환경은 다른 것이다">
코드를 적기만 하는 도구를 편집기라 하고, 번역·실행·디버깅까지 갖춘 것을 통합 개발 환경이라 한다. 그런데 요즘은 경계가 흐릿하다. 가벼운 편집기에 기능을 덧붙여 통합 개발 환경처럼 쓰는 방식이 흔해졌기 때문이다. **어느 것을 쓰든 확인할 것은 같다** — 코드를 적을 수 있는가, 번역기를 부를 수 있는가, 값을 들여다볼 수 있는가. 도구 이름보다 이 셋이 갖춰졌는지가 기준이다.
</MoreBox>
