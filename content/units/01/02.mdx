## 생각 열기 — 번역가와 통역사

외국어로 된 책을 읽어야 한다. 방법은 두 가지다.

하나는 **번역가**에게 책 전체를 맡기는 것이다. 시간이 걸리지만 한 번 끝내 두면 한국어 책이 남는다. 그 뒤로는 번역가 없이 몇 번이든 읽을 수 있고, 읽는 속도도 빠르다.

다른 하나는 **통역사**를 옆에 두는 것이다. 한 문장 읽을 때마다 그 자리에서 옮겨 준다. 기다릴 필요 없이 바로 시작할 수 있다. 그러나 읽는 동안 통역사가 계속 옆에 있어야 하고, 같은 책을 다시 읽을 때도 처음부터 다시 옮겨야 한다.

<InfoBox variant="think" label="함께 생각해 보기">
두 방법 중 어느 쪽이 더 좋은가? 답은 상황에 달려 있다. 한 번 만들어 수만 명에게 배포할 책이라면 번역가가 낫다. 한두 쪽만 급히 확인하려면 통역사가 낫다. 프로그래밍 언어에도 똑같은 두 갈래가 있다.
</InfoBox>

## 고급 언어는 반드시 번역된다

1차시에서 확인한 대로 중앙처리장치가 실행할 수 있는 것은 기계어뿐이다. Python이든 C든 고급 언어로 쓴 코드는 그대로 실행되지 않는다. **기계어로 옮기는 단계를 반드시 거친다.**

옮기는 방식은 앞의 번역가와 통역사처럼 두 갈래로 나뉜다. 실행하기 전에 전체를 미리 옮겨 두는 방식이 컴파일이고, 실행하면서 필요한 만큼 그때그때 옮기는 방식이 해석이다.

## 컴파일러 — 미리 전부 번역한다

<Term ko="컴파일러" en="compiler" desc="소스 코드 전체를 실행 전에 한 번에 번역하는 프로그램" />는 소스 코드 전체를 훑어 기계어로 옮긴다. 그 결과로 나오는 것이 <Term ko="목적 코드" en="object code" desc="기계어로 번역됐지만 아직 혼자 실행되지는 못하는 중간 결과물" />다.

목적 코드는 아직 혼자 실행되지 못한다. 프로그램이 쓰는 화면 출력 기능처럼 미리 만들어져 있는 부분과 이어 붙여야 하기 때문이다. 여러 목적 코드와 라이브러리를 하나로 묶어 실행 파일을 만드는 일을 <Term ko="링커" en="linker" desc="목적 코드와 라이브러리를 묶어 실행 파일로 만드는 프로그램" />가 한다.

이 과정이 끝나면 **실행 파일 하나가 남는다.** 소스 코드도 컴파일러도 필요 없다. 우리가 내려받아 쓰는 프로그램 대부분이 이렇게 만들어진 실행 파일이다. C가 대표적인 컴파일 방식 언어다.

## 인터프리터 — 한 줄씩 그때그때 번역한다

<Term ko="인터프리터" en="interpreter" desc="소스 코드를 실행하면서 한 줄씩 번역해 곧바로 수행하는 프로그램" />는 실행 파일을 만들지 않는다. 소스 코드를 위에서부터 읽어 한 줄을 번역하고 곧바로 실행한 뒤 다음 줄로 넘어간다.

그래서 코드를 고치고 바로 실행해 결과를 볼 수 있다. 대신 프로그램을 실행하려면 **소스 코드와 인터프리터가 늘 함께 있어야 한다.** 번역과 실행을 같이 하므로 같은 계산이라면 실행 파일보다 느리다. Python이 대표적인 인터프리터 방식 언어다.

## 언제 오류를 만나는가

두 방식의 차이가 가장 뚜렷하게 드러나는 곳이 오류를 만나는 시점이다. 같은 실수를 두 언어에 심어 보자. 세 줄을 출력하는 프로그램인데 **마지막 줄에서 `print`를 `prnit`로 잘못 적었다.**

<CodeSample lang="python" caption="셋째 줄에 오타가 있는 Python 코드" expect={"첫째 줄\n둘째 줄\n"} norun="일부러 오류를 내는 예제다. 표준 출력만 적었고, 그 뒤에 오류 메시지가 따라 나온다.">
{`print("첫째 줄")
print("둘째 줄")
prnit("셋째 줄")`}
</CodeSample>

앞의 두 줄은 **출력됐다.** 그리고 세 번째 줄에서 멈추며 `NameError: name 'prnit' is not defined` 라는 오류가 나온다. 인터프리터는 첫 줄부터 차례로 번역해 실행하므로, 세 번째 줄에 닿기 전까지는 오타가 있다는 사실 자체를 모른다.

<CodeSample lang="c" caption="같은 오타를 넣은 C 코드" expect="" norun="일부러 컴파일이 실패하는 예제다. 실행 파일이 만들어지지 않으므로 출력이 없다.">
{`#include <stdio.h>

int main(void)
{
    printf("첫째 줄\\n");
    printf("둘째 줄\\n");
    prntf("셋째 줄\\n");
    return 0;
}`}
</CodeSample>

C는 **아무것도 출력하지 않는다.** 컴파일러가 소스 코드 전체를 먼저 훑어 일곱째 줄의 오타를 찾아내고, `call to undeclared function 'prntf'` 라는 메시지를 낸 뒤 실행 파일을 만들지 않는다. 앞의 두 줄은 옳게 적혀 있지만 실행될 기회가 없다.

<InfoBox variant="info" label="어느 쪽이 유리한가">
둘 다 나름의 장점이 있다. 컴파일러는 프로그램을 남에게 넘기기 전에 문법 오류를 걸러 준다. 실행해 보지 않아도 잘못된 부분을 알려 준다는 뜻이다. 인터프리터는 앞부분이 어디까지 제대로 도는지 눈으로 확인하면서 조금씩 만들어 갈 수 있다. **다만 어느 방식이든 "문법 오류가 없다"가 "계산이 옳다"를 뜻하지는 않는다.**
</InfoBox>

## 같은 계산을 두 언어로

1부터 10까지 더하는 프로그램을 두 언어로 적었다. 상단의 언어 단추로 바꿔 볼 수 있다.

<CodeSample lang="python" caption="1부터 10까지의 합" expect={"1부터 10까지의 합: 55\n"}>
{`total = 0
for i in range(1, 11):
    total += i
print("1부터 10까지의 합:", total)`}
</CodeSample>

<CodeSample lang="c" caption="1부터 10까지의 합" expect={"1부터 10까지의 합: 55\n"}>
{`#include <stdio.h>

int main(void)
{
    int total = 0;
    for (int i = 1; i <= 10; i++) {
        total += i;
    }
    printf("1부터 10까지의 합: %d\\n", total);
    return 0;
}`}
</CodeSample>

결과는 같은 55다. 다른 것은 그 결과에 이르는 길이다. Python 코드는 저장하고 곧바로 실행했다. C 코드는 컴파일해 실행 파일을 만든 뒤 그 파일을 실행했다. 문법의 차이는 2단원에서 하나씩 다룬다.

## 두 방식을 섞은 하이브리드

컴파일과 해석은 서로 배타적이지 않다. 둘을 섞은 <Term ko="하이브리드 방식" en="hybrid" desc="소스 코드를 중간 형태로 컴파일한 뒤 그것을 해석해 실행하는 방식" />도 널리 쓰인다.

Java가 대표적이다. Java 컴파일러는 소스 코드를 특정 중앙처리장치의 기계어가 아니라 <Term ko="바이트 코드" en="byte code" desc="특정 중앙처리장치가 아니라 가상 머신이 해석하도록 만든 중간 코드" />로 번역한다. 그 바이트 코드를 <Term ko="가상 머신" en="virtual machine" desc="바이트 코드를 해석해 실제 기계에서 실행해 주는 프로그램" />이 해석해 실행한다. 한 번 컴파일한 바이트 코드를 가상 머신이 있는 어느 기종에서나 쓸 수 있다는 것이 이 방식의 이점이다.

<InfoBox variant="tip" label="Python도 실은 두 단계를 거친다">
Python은 인터프리터 방식 언어로 분류하지만, 실제로는 소스 코드를 바이트 코드로 한 번 바꾼 뒤 그것을 해석해 실행한다. 그래서 **"이 언어는 컴파일 언어다"라는 말은 언어 이름보다 그 언어를 실행하는 방법에 달려 있다.** C를 한 줄씩 해석하는 프로그램도, Python을 실행 파일로 묶어 주는 도구도 실제로 존재한다.
</InfoBox>

## 더 알아보기

<MoreBox tag="심화" title="느린 인터프리터를 빠르게 — JIT 컴파일">
인터프리터 방식의 약점은 속도다. 같은 반복문을 수만 번 돌 때, 그 안의 코드를 매번 다시 번역하는 것은 낭비다. 그래서 **자주 실행되는 부분만 실행 중에 기계어로 컴파일해 두고 다음부터는 그것을 쓰는** 방법이 나왔다. 실행하는 그때 컴파일하므로 적시 컴파일(JIT, Just-In-Time compilation)이라 한다. 오늘날 웹 브라우저의 JavaScript 실행기와 Java 가상 머신이 이 방법을 쓴다.
</MoreBox>

<MoreBox tag="인물" title="최초의 컴파일러를 만든 그레이스 호퍼">
1952년, 미국의 수학자이자 해군 장교였던 **그레이스 호퍼**는 사람이 읽을 수 있는 기호로 적은 코드를 기계어로 바꿔 주는 프로그램 A-0를 만들었다. 최초의 컴파일러로 평가받는다. 당시에는 "컴퓨터에게 영어에 가까운 말로 지시한다"는 생각 자체가 받아들여지지 않았다고 한다. 그가 참여한 COBOL은 이후 수십 년간 금융·행정 업무 프로그램의 표준이 되었다.
</MoreBox>

<MoreBox tag="실무" title="컴파일 오류와 실행 오류는 다른 것이다">
컴파일 단계에서 걸리는 것은 **문법이 어긋난 코드**다. 괄호가 안 닫혔거나 없는 이름을 불렀거나 자료형이 맞지 않는 경우다. 그런데 문법이 완벽해도 계산이 틀리거나 프로그램이 중간에 멈추는 일은 얼마든지 있다. 0으로 나누기, 없는 파일 열기, 조건을 거꾸로 쓴 경우가 그렇다. 이런 것은 컴파일러가 잡아 주지 못하고 **실행해 봐야** 드러난다. 그래서 컴파일 성공은 출발점일 뿐이며, 5차시에서 다루는 테스트가 필요하다.
</MoreBox>
