## 생각 열기 — 세 반의 평균을 구하려면

반마다 평균을 내야 한다. 4차시에서 배운 것으로 하면 이렇게 된다.

```text
일반 = [88, 92, 75]
합계 = 0
for 점수 in 일반:
    합계 += 점수
print("1반 평균:", 합계 / len(일반))

이반 = [70, 80, 90]
합계 = 0
for 점수 in 이반:
    합계 += 점수
print("2반 평균:", 합계 / len(이반))

삼반 = [100, 60, 80]
...
```

같은 다섯 줄이 세 번 나온다.

<InfoBox variant="think" label="함께 생각해 보기">
이 코드에서 **반마다 달라지는 것**은 무엇이고 **똑같은 것**은 무엇인가? 그리고 나중에 "평균을 소수 첫째 자리까지 보이라"는 요구가 들어오면 몇 곳을 고쳐야 하는가? 1단원 5차시에서 "같은 코드를 여러 곳에 복사하지 않는다"고 한 이유가 여기서 보인다.
</InfoBox>

## 함수 — 하는 일에 이름을 붙인다

<Term ko="함수" en="function" desc="하는 일에 이름을 붙여 묶어 놓은 코드 덩어리. 이름으로 불러 쓴다" />는 코드 덩어리에 이름을 붙여, 필요할 때마다 이름으로 불러 쓰는 장치다.

**3단원 3차시의 「부품」이 코드에서는 함수다.** 그때 부품의 겉모습을 다섯 칸으로 못 박았다 — 이름·받는 것·돌려주는 것·하는 일·실패하면. 그 다섯 칸이 함수를 만들 때 그대로 필요하다.

<CodeSample lang="python" caption="평균 구하기를 함수로 묶기" expect={"1반 평균: 85.0\n2반 평균: 80.0\n3반 평균: 80.0\n"}>
{`def 평균(점수들):
    return sum(점수들) / len(점수들)

일반 = [88, 92, 75]
이반 = [70, 80, 90]
삼반 = [100, 60, 80]

print(f"1반 평균: {평균(일반):.1f}")
print(f"2반 평균: {평균(이반):.1f}")
print(f"3반 평균: {평균(삼반):.1f}")`}
</CodeSample>

<CodeSample lang="c" caption="평균 구하기를 함수로 묶기" expect={"1반 평균: 85.0\n2반 평균: 80.0\n3반 평균: 80.0\n"}>
{`#include <stdio.h>

double average(const int a[], int n)
{
    int sum = 0;
    for (int i = 0; i < n; i++) sum += a[i];
    return (double)sum / n;
}

int main(void)
{
    int c1[] = {88, 92, 75};
    int c2[] = {70, 80, 90};
    int c3[] = {100, 60, 80};

    printf("1반 평균: %.1f\\n", average(c1, 3));
    printf("2반 평균: %.1f\\n", average(c2, 3));
    printf("3반 평균: %.1f\\n", average(c3, 3));
    return 0;
}`}
</CodeSample>

### 무엇이 좋아졌나

- 평균 계산이 **한 곳에만** 있다. 고칠 때 한 곳만 고친다.
- `평균(일반)` 이라는 말이 **무엇을 하는지 그대로 읽힌다.** 주석이 필요 없다.
- 반이 열 개로 늘어도 계산 부분은 그대로다.

<InfoBox variant="tip" label="함수 이름이 곧 설명이다">
`평균(일반)` 을 보면 안을 안 열어 봐도 무엇이 나올지 안다. 1차시에서 "좋은 이름이 주석을 줄인다"고 한 것이 함수에서 가장 크게 드러난다. **하는 일을 한 낱말로 말할 수 있으면 좋은 함수**이고, 이름 짓기가 어려우면 한 가지 일이 아닐 가능성이 크다(3단원 3차시).
</InfoBox>

**우리는 이미 라이브러리 함수를 계속 써 왔다.** `print`, `len`, `sum`, `int`, `input` 이 전부 함수다. `sum(점수들)` 은 안이 어떻게 되어 있는지 몰라도 쓸 수 있었다.

<InfoBox variant="info" label="이것이 3단원의 「남의 속을 몰라도 쓴다」다">
3단원 3차시에서 부품을 쪼개는 기준으로 "남의 속을 몰라도 쓸 수 있는가"를 들었다. `sum` 을 쓸 때 우리가 한 일이 정확히 그것이다. **함수는 안쪽 사정을 감춰 주는 벽**이고, 그 벽 덕분에 한 번에 생각할 것의 크기가 줄어든다.
</InfoBox>

## C는 쓰기 전에 알려야 한다

C 예제에서 `average` 가 `main` **위에** 있다. 이유가 있다. C는 위에서 아래로 읽으며 컴파일하므로, 부르는 곳보다 함수가 먼저 나와야 한다.

아래에 두려면 위쪽에 **어떤 함수가 있을지 미리 알려 주는 한 줄**을 적는다.

```text
double average(const int a[], int n);   ← 이런 함수가 있다는 예고

int main(void) { ... average(...) ... }

double average(const int a[], int n) { ... }   ← 실제 내용
```

Python은 이런 예고가 필요 없다. 다만 **부르는 시점에는 정의가 이미 실행되어 있어야** 하므로, 관례로 함수를 위쪽에 모아 둔다.

## 더 알아보기

<MoreBox tag="심화" title="같은 코드가 두 번이면 아직 참을 만하다">
"같은 코드가 보이면 무조건 함수로 묶어라"가 늘 맞는 것은 아니다. 두 곳에 비슷한 코드가 있는데 **앞으로 서로 다르게 바뀔 것 같으면**, 억지로 묶은 함수가 오히려 짐이 된다. 두 쪽 요구를 다 만족시키려고 조건과 매개변수가 계속 늘어나기 때문이다.

실무에서 흔히 쓰는 기준은 **세 번째로 같은 코드를 적게 될 때 묶는다**는 것이다. 세 번 나타났다면 앞으로도 나타날 가능성이 크고, 세 곳의 공통점이 무엇인지도 그때쯤 분명해진다. 다만 이 차시의 평균처럼 **하는 일이 명확한 계산**은 두 번째부터 묶어도 좋다.
</MoreBox>

<MoreBox tag="실무" title="함수로 나누면 테스트할 수 있다">
3단원 7차시에서 단위 테스트를 다뤘다. 부품 하나를 따로 떼어 정한 입력에 정한 결과가 나오는지 확인하는 것이었다. **함수가 아니면 그것을 할 수 없다.** 코드가 한 덩어리로 흘러 있으면 중간의 평균 계산만 떼어 시험할 방법이 없다.

그래서 "테스트하기 쉬운 코드"와 "함수로 잘 나뉜 코드"는 거의 같은 말이다. 나중에 테스트를 붙이려면 지금 나눠 두어야 한다. 16차시에서 프로그램 전체를 함수로 나눌 때 이 이야기를 다시 다룬다.
</MoreBox>

<MoreBox tag="심화" title="함수를 부르는 값">
함수를 부르는 일이 공짜는 아니다. 값을 넘기고 돌아올 자리를 기억해 두는 준비가 필요하다. 그래서 아주 짧은 계산을 수백만 번 부르면 그 준비 비용이 눈에 띌 수 있다.

그렇다고 함수를 아끼는 것은 대체로 잘못된 판단이다. 1단원 6차시에서 다룬 대로 **프로그램이 느린 원인은 대개 알고리즘이지 함수 호출이 아니다.** 읽기 쉬운 코드로 먼저 만들고, 정말 느리면 어디가 느린지 재어 본 뒤 고치는 것이 순서다. 재어 보지 않고 짐작으로 고치는 것을 실무에서는 가장 흔한 낭비로 본다.
</MoreBox>
