## 생각 열기 — "평균을 낸다"의 안쪽

3차시 설계서에 `summarize` 부품을 이렇게 적었다.

> **받는 것**: 정수 목록 · **돌려주는 것**: 결과 묶음
> **하는 일**: 범위 밖 값을 빼고 인원·평균·최고·최저를 낸다

이제 이 부품을 맡은 사람이 코드를 쓰려고 앉았다. 그런데 손이 멈춘다. 값을 하나씩 보면서 무엇을 어떤 순서로 갱신해야 하는지, 최고점의 처음 값은 무엇으로 두어야 하는지가 적혀 있지 않기 때문이다.

<InfoBox variant="think" label="함께 생각해 보기">
최고점을 찾을 때 **처음 값을 0으로 두면** 어떻게 될까? 우리 점수는 0~100이니 괜찮아 보인다. 그런데 1단원 7차시 활동의 마지막 줄을 떠올려 보자 — 입력이 −2, −8, −5 였을 때 최댓값을 0으로 두고 시작한 절차는 틀린 답을 냈다. 이런 함정을 코드를 쓰기 전에 찾으려면 무엇을 해야 할까?
</InfoBox>

## 부품마다 알고리즘을 적는다

설계서가 **부품의 겉모습**을 정했다면, 알고리즘은 **부품의 안쪽**을 정한다. 1단원 7차시에서 익힌 의사 코드를 그대로 쓴다.

`summarize`의 알고리즘은 이렇게 된다.

```text
[summarize — 점수 목록에서 통계를 낸다]
 1  입력: 점수 목록
 2  출력: 결과 묶음, 또는 쓸 수 있는 값이 없으면 "없음"
 3
 4  인원 ← 0
 5  제외 ← 0
 6  합계 ← 0
 7  최고 ← 아직 없음
 8  최저 ← 아직 없음
 9
10  점수 목록의 각 점수에 대하여 되풀이한다
11      만약 is_valid(점수) 가 거짓이면
12          제외 ← 제외 + 1
13      아니면
14          만약 인원 = 0 이면
15              최고 ← 점수
16              최저 ← 점수
17          아니면
18              만약 점수 > 최고 이면  최고 ← 점수
19              만약 점수 < 최저 이면  최저 ← 점수
20          합계 ← 합계 + 점수
21          인원 ← 인원 + 1
22
23  만약 인원 = 0 이면
24      "없음" 을 돌려주고 끝낸다
25
26  평균 ← 합계 ÷ 인원
27  (인원, 제외, 평균, 최고, 최저) 를 돌려준다
```

**14~16줄**이 생각 열기의 함정을 막는 부분이다. 최고·최저를 0이나 100 같은 특정 값으로 시작하지 않고, **첫 번째 쓸 수 있는 점수를 그대로 넣는다.** 이렇게 하면 점수 범위가 무엇이든 옳게 동작한다.

**23~24줄**은 쓸 수 있는 값이 하나도 없을 때 빠져나가는 출구다. 이 줄이 없으면 26줄에서 **0으로 나누게 된다.**

마지막 두 줄이 중요하다. **예외를 찾았다고 전부 여기서 다뤄야 하는 것은 아니다.** "모두 같은 점수"는 따져 보니 문제가 없었고, "숫자가 아닌 값"은 다른 부품의 책임이다. 3차시 설계서에서 `read_scores`의 「실패하면」 칸에 그렇게 적어 두었다.

<InfoBox variant="tip" label="예외를 찾는 네 가지 물음">
알고리즘을 다 적었으면 이렇게 물어본다.

1. **아무것도 없으면?** — 빈 목록, 0개, 빈 문자열
2. **하나뿐이면?** — 비교나 나누기가 들어간 곳에서 자주 걸린다
3. **경계에 딱 걸리면?** — 0과 100, 첫 번째와 마지막
4. **나눗셈이 있는가?** — 나누는 값이 0이 될 수 있는 길이 있는가
</InfoBox>

## 책상 검사 — 손으로 따라가 본다

알고리즘을 적었으면 **실행해 보기 전에 손으로 따라가 본다.** 이것을 책상 검사라 한다. 변수마다 칸을 만들고 한 줄씩 짚어 가며 값을 적는다.

입력이 `88, 92, −5` 일 때 `summarize`를 따라가면 이렇게 된다.

| 단계 | 보는 점수 | is_valid | 인원 | 제외 | 합계 | 최고 | 최저 |
|---|---|---|---|---|---|---|---|
| 시작 (4~8줄) | — | — | 0 | 0 | 0 | 아직 없음 | 아직 없음 |
| 1회 (11~21줄) | 88 | 참 | 1 | 0 | 88 | 88 | 88 |
| 2회 | 92 | 참 | 2 | 0 | 180 | 92 | 88 |
| 3회 | −5 | 거짓 | 2 | 1 | 180 | 92 | 88 |
| 끝 (23줄) | — | — | 인원이 0이 아니므로 계속 진행 | | | | |
| 끝 (26줄) | — | — | 평균 = 180 ÷ 2 = **90.0** | | | | |

돌려주는 값은 인원 2, 제외 1, 평균 90.0, 최고 92, 최저 88이다. **손으로 낸 이 값이 나중에 테스트의 기대 결과가 된다.**

<InfoBox variant="warn" label="프로그램을 돌려서 기대 결과를 정하지 않는다">
2차시에서 한 이야기가 여기서도 그대로다. 코드를 짜고 실행해서 나온 값을 "정답"으로 삼으면, 코드가 틀렸을 때도 통과해 버린다. **기대 결과는 손으로 먼저 계산해 두어야** 대조하는 뜻이 생긴다. 책상 검사가 그 일을 한다.
</InfoBox>

책상 검사는 특히 아래 입력으로 해 보면 좋다.

- **평범한 입력** — 흐름이 맞는지 본다
- **값이 하나뿐인 입력** — 첫 값 처리(14~16줄)가 맞는지 본다
- **전부 걸러지는 입력** — 출구(23~24줄)로 빠지는지 본다

## 알고리즘을 다 적었는지 확인하는 법

1. 설계서의 부품마다 알고리즘이 하나씩 있는가?
2. 각 알고리즘의 **첫 줄에 입력, 둘째 줄에 출력**이 적혀 있는가?
3. 나눗셈이 있는 곳마다 **나누는 값이 0이 될 길**을 막았는가?
4. 되풀이하는 부분마다 **무엇이 변해서 끝나는지** 말할 수 있는가? (1단원 6·7차시)
5. 설계서의 「실패하면」 칸에 적은 내용이 알고리즘에 실제로 들어가 있는가?

<InfoBox variant="info" label="5번을 특히 확인한다">
설계서에는 "쓸 수 있는 값이 없으면 없음을 돌려준다"고 적어 놓고, 알고리즘에는 그 줄을 빠뜨리는 일이 흔하다. 문서와 문서 사이에서 요구가 새는 것이다. **설계서와 알고리즘을 나란히 놓고 한 줄씩 대조**하는 데 몇 분이면 된다.
</InfoBox>

## 활동

<Activity kind="프로젝트" title="핵심 기능 2개의 알고리즘을 의사 코드로 작성" time={45}>

3차시 설계서에서 정한 부품 중 **핵심 두 개**를 골라 알고리즘을 적는다.

**1단계 — 의사 코드로 적는다 (15분)**

부품마다 아래 형식을 지킨다.

```text
[부품 이름 — 한 줄 설명]
 1  입력: …
 2  출력: …
 3
 4  (여기서부터 절차)
```

- 줄 번호를 붙인다. 나중에 "몇 줄에서 다룬다"고 가리킬 수 있어야 한다.
- 들여쓰기로 조건과 반복의 범위를 나타낸다.
- 저장은 `←` 로 적는다.

**2단계 — 예외를 찾는다 (10분)**

네 가지 물음을 던지고 찾은 것을 표로 적는다.

| 예외 상황 | 언제 생기는가 | 다루지 않으면 | 몇 줄에서 다루는가 |
|---|---|---|---|
| | | | |

**「다루지 않으면」 칸이 "문제없다"인 항목도 표에 남긴다.** 따져 봤다는 기록이 되기 때문이다. 다른 부품이 담당하는 것도 그렇게 적는다.

찾은 예외 중 알고리즘에 빠진 것이 있으면 1단계로 돌아가 줄을 추가한다.

**3단계 — 책상 검사 (15분)**

세 가지 입력으로 손으로 따라간다. **계산기를 쓰지 않는다.**

| 입력 | 왜 이 입력인가 | 손으로 낸 결과 |
|---|---|---|
| | 평범한 경우 | |
| | 값이 하나뿐인 경우 | |
| | 전부 걸러지거나 비어 있는 경우 | |

변수가 여럿이면 변수마다 칸을 만든 표로 한 줄씩 적는다.

**4단계 — 짝과 바꿔 읽기 (5분)**

짝의 의사 코드만 보고 **적힌 그대로만** 따라가 본다. 1단원 1차시 활동과 같은 규칙이다 — 적히지 않은 판단은 하지 않는다. 막히는 곳에 표시해 돌려준다.

3단계에서 손으로 낸 결과는 **버리지 말고 보관한다.** 7차시 테스트 사례에서 그대로 쓴다.

</Activity>

## 더 알아보기

<MoreBox tag="심화" title="한 번만 훑고 끝내기">
위 알고리즘은 점수 목록을 **한 번만** 지나가면서 인원·합계·최고·최저를 모두 구한다. 나눠서 생각하면 "합계를 구하려고 한 번, 최고를 찾으려고 또 한 번" 훑고 싶어지는데, 그러면 목록을 네 번 지나가게 된다. 자료가 300개일 때는 차이를 못 느끼지만 30만 개가 되면 달라진다. **여러 값을 함께 구할 수 있으면 한 번에 구한다** — 1단원 6차시에서 다룬 효율의 실제 사례다. 다만 한 번에 너무 많은 일을 넣으면 읽기 어려워지므로, 읽기와 속도 사이에서 판단해야 한다.
</MoreBox>

<MoreBox tag="실무" title="예외를 어디서 다룰지 정하는 문제">
"숫자가 아닌 값"을 `read_scores`에서 걸러 넘기기로 한 것은 판단이었다. `summarize`에서 다루게 할 수도 있었다. 어느 쪽이 나은가? 일반적으로 **잘못된 값은 들어오는 문 앞에서 막는 편**이 낫다. 안쪽 부품들이 "여기 오는 값은 이미 정수다"라고 믿고 만들어질 수 있기 때문이다. 반대로 문 앞에서 막지 않으면 모든 부품이 같은 검사를 되풀이해야 한다. 이 판단을 설계 단계에서 정해 문서에 적어 두는 것이 3차시의 「실패하면」 칸이다.
</MoreBox>

<MoreBox tag="심화" title="의사 코드는 언어가 아니다">
의사 코드에는 정해진 문법이 없다. `←` 대신 `=`를 써도 되고, 한국어 대신 영어로 적어도 된다. 중요한 것은 **읽는 사람이 한 가지 뜻으로만 읽는가**다. 그래서 팀 안에서 표기를 통일해 두면 좋다. 다만 의사 코드를 너무 코드처럼 적으면 특정 언어의 문법에 묶여, 다른 언어로 옮길 때 도움이 안 된다. **Python으로도 C로도 옮길 수 있는 수준**에서 멈추는 것이 알맞다. 이 단원의 알고리즘 하나가 5차시에서 두 언어로 갈라지는 것을 직접 보게 된다.
</MoreBox>
