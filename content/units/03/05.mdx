## 알고리즘을 두 언어로 옮겨 보기

4차시의 알고리즘 하나가 언어에 따라 어떻게 갈라지는지 보자. 먼저 평균을 내는 부분만 떼어 낸다. **알고리즘의 23~26줄** — 인원이 0이면 빠져나가고, 아니면 나눈다.

<CodeSample lang="python" caption="평균 부분만 떼어 낸 구현" expect={"평균: 83.8\n빈 목록: None\n"}>
{`def average(scores):
    if len(scores) == 0:
        return None
    return sum(scores) / len(scores)

scores = [88, 92, 75, 100, 64]
print("평균:", average(scores))
print("빈 목록:", average([]))`}
</CodeSample>

<CodeSample lang="c" caption="평균 부분만 떼어 낸 구현" expect={"평균: 83.8\n빈 목록: 평균을 낼 수 없다\n"}>
{`#include <stdio.h>

/* 점수가 없으면 평균을 낼 수 없다. 성공 여부를 반환값으로 알린다. */
int average(const int scores[], int n, double *out)
{
    if (n == 0) return 0;
    int sum = 0;
    for (int i = 0; i < n; i++) sum += scores[i];
    *out = (double)sum / n;
    return 1;
}

int main(void)
{
    int scores[] = {88, 92, 75, 100, 64};
    double avg;

    if (average(scores, 5, &avg))
        printf("평균: %.1f\\n", avg);
    if (!average(scores, 0, &avg))
        printf("빈 목록: 평균을 낼 수 없다\\n");
    return 0;
}`}
</CodeSample>

<InfoBox variant="warn" label="C의 정수 나눗셈 함정">
`sum / n` 을 그대로 쓰면 419 ÷ 5 가 **83** 이 된다. 소수 부분이 버려지기 때문이다. 명세서 F3은 "소수점 첫째 자리까지"를 요구하므로 이대로면 요구 사항 위반이다. `(double)sum / n` 처럼 한쪽을 실수로 바꿔야 83.8이 나온다. **설계에는 없던 문제가 언어를 고른 뒤에 생긴 것**이며, 이런 것을 발견하면 기록해 두어야 한다.
</InfoBox>

## 구현 중 설계와 달라진 것을 기록한다

코드를 쓰다 보면 설계가 틀렸거나 부족했다는 것을 알게 된다. 위의 C 반환값 문제가 그렇다. 설계서에는 "쓸 수 있는 값이 없으면 없음을 돌려준다"고만 적었는데, C에는 "없음"이라는 값이 없었다.

이때 **코드만 고치고 문서를 그대로 두면** 문서를 아무도 믿지 않게 된다. 그래서 짧게라도 남긴다.

| 날짜 | 무엇이 달라졌나 | 왜 | 문서 반영 |
|---|---|---|---|
| 구현 1일차 | `average`가 C에서는 값을 두 개 돌려주는 형태가 됨 | C에는 "없음"에 해당하는 값이 없어, 성공 여부를 반환값으로 하고 결과는 포인터로 넘김 | 설계서 「돌려주는 것」 칸에 언어별 표기 추가 |
| 구현 1일차 | 나눗셈에 `(double)` 추가 | 정수끼리 나누면 소수가 잘려 F3을 못 지킴 | 알고리즘 26줄에 주석 추가 |

<InfoBox variant="tip" label="'설계가 틀렸다'는 나쁜 소식이 아니다">
구현하면서 설계의 빈틈이 드러나는 것은 정상이다. 3차시에서 말한 대로 **설계가 바뀌는 것 자체는 실패가 아니다.** 문제는 바뀐 것을 아무도 모르게 두는 것이다. 표 한 줄이면 충분하다.
</InfoBox>

**2단계 — 껍데기를 만든다 (10분)**

설계서의 부품을 전부 빈 껍데기로 만들고, 주 프로그램에서 순서대로 불러 본다. 안은 정해진 값 하나를 돌려주게 둔다.

- 이 단계에서 **한 번 실행해 본다.** 결과는 엉터리여도 된다.
- 실행이 안 되면 부품끼리 이어지는 부분이 틀린 것이다. 여기서 잡고 넘어간다.

**3단계 — 안쪽부터 채운다 (25분)**

남을 부르지 않는 부품부터 진짜로 만든다. **하나 채울 때마다 실행해 본다.**

| 부품 | 채운 뒤 확인한 입력 | 나온 결과 | 기대한 결과 (4차시 책상 검사) | 같은가 |
|---|---|---|---|---|
| | | | | |

4차시 책상 검사에서 손으로 낸 값을 「기대한 결과」에 적는다. **지금 프로그램이 낸 값을 적지 않는다.**

**4단계 — 달라진 것을 기록한다 (5분)**

설계와 다르게 만든 부분이 있으면 표로 남긴다.

| 무엇이 달라졌나 | 왜 | 문서에 반영했는가 |
|---|---|---|

한 부품도 완성하지 못했어도 괜찮다. **껍데기까지는 반드시 만들어 둔다.** 6차시에서 그것을 합친다.

## 더 알아보기

<MoreBox tag="심화" title="가짜 부품으로 먼저 돌려 보기">
3차시에서 겉모습을 못 박으면 아직 없는 부품도 흉내 낼 수 있다고 했다. 껍데기 단계가 바로 그것이다. `summarize`가 아직 없어도 "인원 5명, 평균 83.8" 이라고 정해진 값을 돌려주게 만들어 두면, `report`를 맡은 사람은 그것으로 출력 형식을 완성할 수 있다. 실무에서는 이런 임시 코드를 만들어 두고 **여러 사람이 서로를 기다리지 않고 동시에 작업한다.** 다만 진짜 부품이 완성되면 임시 코드를 반드시 지워야 한다. 남겨 두면 나중에 왜 이 값이 나오는지 아무도 모르게 된다.
</MoreBox>

<MoreBox tag="실무" title="'왜'를 적은 주석이 살아남는다">
`합계 = 합계 + 점수` 옆에 "점수를 더한다"고 적은 주석은 코드가 바뀌면 곧 거짓말이 된다. 반대로 "결시생은 0점이 아니라 제외해야 하므로 여기서 걸러 낸다"처럼 **판단의 이유**를 적은 주석은 코드가 바뀌어도 오래 쓸모가 있다. 위 C 예제의 `/* 점수가 없으면 평균을 낼 수 없다 */` 도 같은 종류다 — 왜 반환값을 이렇게 만들었는지를 설명한다. 1단원 5차시와 9차시에서 되풀이해 나온 이야기이며, 실제로 이것을 지키는 사람은 많지 않다.
</MoreBox>

<MoreBox tag="심화" title="언어가 표현을 바꾸는 지점">
같은 알고리즘이 언어에 따라 갈라지는 곳은 대체로 정해져 있다. **여러 값을 한 번에 돌려줄 수 있는가**(Python은 가능, C는 포인터가 필요), **"값이 없음"을 나타낼 수 있는가**(Python은 `None`, C는 따로 약속해야 한다), **자료의 길이를 자료가 아는가**(Python은 알고, C의 배열은 모른다). 새 언어를 배울 때 이 세 가지가 어떻게 되는지 먼저 확인하면 알고리즘을 옮기기가 훨씬 수월하다.
</MoreBox>
