## 생각 열기 — 각자는 되는데 합치니 안 된다

모둠에서 부품을 나눠 만들었다. 각자 실행해 보니 다 잘 됐다. 그런데 합쳐 놓으니 이런 일이 생겼다.

- A가 만든 입력 부품은 점수를 **문자열**로 넘겼는데, B의 통계 부품은 **정수**를 기다렸다.
- B는 결과를 `(인원, 평균, 최고, 최저)` 순으로 돌려줬는데, C의 출력 부품은 `(평균, 인원, …)` 순으로 받았다.
- 셋 다 `is_valid` 를 각자 만들어 넣어 두었고, 그중 하나는 `0 < 점수` 로 적혀 있었다.

<InfoBox variant="think" label="함께 생각해 보기">
세 가지 모두 **각 부품만 보면 문제가 없다.** 그런데 합치면 틀린다. 이런 문제를 합치기 전에 막으려면 3차시에서 무엇을 했어야 할까? 그리고 이미 이렇게 됐다면 어디부터 손대야 할까?
</InfoBox>

## 합쳐진 프로그램

3차시 설계의 부품들을 실제로 이어 붙이면 이렇게 된다. `summarize` 가 `is_valid` 를 부르고, `report` 가 `summarize` 의 결과를 받는다.

<CodeSample lang="python" caption="부품을 이어 붙인 프로그램" expect={"인원 5명 (제외 2건)\n평균 83.8  최고 100  최저 64\n쓸 수 있는 점수가 없다\n"}>
{`def is_valid(score):
    return 0 <= score <= 100

def summarize(scores):
    valid = [s for s in scores if is_valid(s)]
    if not valid:
        return None
    return {
        "count": len(valid),
        "dropped": len(scores) - len(valid),
        "avg": sum(valid) / len(valid),
        "high": max(valid),
        "low": min(valid),
    }

def report(result):
    if result is None:
        print("쓸 수 있는 점수가 없다")
        return
    print(f"인원 {result['count']}명 (제외 {result['dropped']}건)")
    print(f"평균 {result['avg']:.1f}  최고 {result['high']}  최저 {result['low']}")

report(summarize([88, 92, 75, 100, 64, -5, 120]))
report(summarize([-1, 200]))`}
</CodeSample>

<CodeSample lang="c" caption="부품을 이어 붙인 프로그램" expect={"인원 5명 (제외 2건)\n평균 83.8  최고 100  최저 64\n쓸 수 있는 점수가 없다\n"}>
{`#include <stdio.h>

typedef struct {
    int count;
    int dropped;
    double avg;
    int high;
    int low;
} Summary;

int is_valid(int score)
{
    return score >= 0 && score <= 100;
}

/* 쓸 수 있는 점수가 하나도 없으면 0을 돌려준다 */
int summarize(const int scores[], int n, Summary *out)
{
    int sum = 0;
    out->count = 0;
    out->dropped = 0;

    for (int i = 0; i < n; i++) {
        if (!is_valid(scores[i])) {
            out->dropped++;
            continue;
        }
        /* 첫 번째 쓸 수 있는 점수를 최고·최저의 기준으로 삼는다 */
        if (out->count == 0 || scores[i] > out->high) out->high = scores[i];
        if (out->count == 0 || scores[i] < out->low) out->low = scores[i];
        sum += scores[i];
        out->count++;
    }
    if (out->count == 0) return 0;
    out->avg = (double)sum / out->count;
    return 1;
}

void report(const int scores[], int n)
{
    Summary s;
    if (!summarize(scores, n, &s)) {
        printf("쓸 수 있는 점수가 없다\\n");
        return;
    }
    printf("인원 %d명 (제외 %d건)\\n", s.count, s.dropped);
    printf("평균 %.1f  최고 %d  최저 %d\\n", s.avg, s.high, s.low);
}

int main(void)
{
    int a[] = {88, 92, 75, 100, 64, -5, 120};
    int b[] = {-1, 200};
    report(a, 7);
    report(b, 2);
    return 0;
}`}
</CodeSample>

두 프로그램의 출력이 **글자 단위로 같다.** 3차시 설계서에 출력 형식을 띄어쓰기까지 적어 둔 덕분이다. 형식을 정해 두지 않았다면 여기서 두 언어의 결과가 달라졌을 것이다.

  ]}
/>

<InfoBox variant="warn" label="C 쪽에 4차시의 함정이 그대로 남아 있다">
C의 `summarize` 에는 `out->count == 0 ||` 라는 조건이 붙어 있다. 4차시 알고리즘 14~16줄, 곧 **첫 번째 쓸 수 있는 점수를 최고·최저의 기준으로 삼는다**는 부분이다. Python은 `max()`가 알아서 처리해 주므로 이 코드가 보이지 않는다. **같은 알고리즘인데 한쪽에서만 실수할 여지가 있는 것**이다. 언어가 대신 해 주는 일이 무엇인지 알아 두어야 하는 이유다.
</InfoBox>

## 합칠 때는 버전 관리가 필요하다

1단원 9차시에서 다룬 문제가 지금 실제로 생긴다. 세 사람이 각자 고친 파일을 하나로 만들어야 한다.

- **합치기 전에 최신 내용을 받아 온다.** 낡은 것 위에 고치면 충돌이 늘어난다.
- **한 사람이 한 부품만 고친다.** 같은 함수를 둘이 고치면 같은 줄에서 충돌한다.
- **한 번에 한 가지씩 올린다.** "is_valid 구현" 과 "출력 형식 수정" 을 한 묶음으로 올리면 되돌릴 때 필요한 것까지 사라진다.
- **충돌은 고장이 아니다.** 두 수정을 나란히 읽고 어느 쪽을 남길지 사람이 정한다.

버전 관리 도구를 쓰지 않는다면 **합치는 담당자를 한 명 정하고 나머지는 그 사람에게 부품 파일만 넘긴다.** 여럿이 동시에 같은 파일을 고치는 상황만 피해도 대부분의 문제가 사라진다.

## 어긋난 곳을 좁히는 법

합쳤는데 결과가 틀렸다면 순서대로 좁힌다.

1. **어느 입력에서 틀리는가** — 4차시 책상 검사의 세 입력을 모두 넣어 본다. 전부 틀리는지, 특정 입력에서만 틀리는지 가른다.
2. **어느 부품에서 틀어지는가** — 부품 하나만 따로 불러 손으로 낸 값과 대조한다.
3. **부품 안 어디서 틀어지는가** — 값을 중간에 찍어 보거나 디버거의 중단점을 건다(1단원 8차시).
4. **고친 뒤 앞의 것을 다시 본다** — 되던 기능이 깨지지 않았는지 확인한다.

<InfoBox variant="info" label="찍어 본 출력문은 반드시 지운다">
값을 확인하려고 끼워 넣은 출력문을 남겨 두면, 쓰는 사람에게 알 수 없는 값이 보인다. 명세서의 출력 형식과도 어긋난다. **확인이 끝나면 지운다.** 지웠는지 확인하는 가장 쉬운 방법은 합친 뒤 한 번 더 실행해 출력이 설계서의 형식과 정확히 같은지 보는 것이다.
</InfoBox>

## 더 알아보기

<MoreBox tag="심화" title="위에서부터 붙이기와 아래에서부터 붙이기">
통합에는 두 방향이 있다. 주 프로그램부터 붙이고 아래쪽 부품은 가짜로 채우는 방식과, 가장 안쪽 부품부터 완성해 위로 올라가는 방식이다. 앞의 것은 **전체 흐름을 일찍 볼 수 있고**, 뒤의 것은 **확인이 끝난 것 위에 쌓아 올릴 수 있다.** 이 차시에서는 껍데기로 전체를 먼저 돌려 본 뒤 안쪽부터 채웠으니 둘을 섞어 쓴 셈이다. 실무에서도 대개 섞어 쓴다.
</MoreBox>

<MoreBox tag="실무" title="합치는 일을 매일 한다">
학교 프로젝트는 마지막에 몰아서 합치기 쉽다. 그런데 그렇게 하면 어긋난 곳이 한꺼번에 쏟아져 나온다. 실무에서는 **하루에 한 번 이상 합치고 자동으로 시험을 돌린다.** 합치는 간격이 짧을수록 한 번에 처리할 어긋남이 적어지기 때문이다. 모둠 프로젝트에서도 "수업 끝나기 10분 전에 그날 만든 것을 합쳐 본다"는 약속 하나만으로 마지막 날의 고생이 크게 줄어든다.
</MoreBox>

<MoreBox tag="심화" title="사전과 구조체 — 무엇이 다른가">
Python의 사전은 실행 중에 항목을 넣고 뺄 수 있다. 편한 대신 **`result['cont']` 처럼 이름을 잘못 적어도 실행하기 전에는 아무도 모른다.** C의 구조체는 항목을 미리 선언하므로 이름을 잘못 적으면 컴파일 단계에서 걸린다. 1단원 2차시에서 다룬 "오류를 만나는 시점"의 차이가 여기서도 그대로 나타난다. 어느 쪽이 낫다기보다, **자기가 쓰는 언어가 무엇을 실행 전에 잡아 주고 무엇을 안 잡아 주는지** 알고 그만큼 테스트로 메우는 것이 중요하다.
</MoreBox>
